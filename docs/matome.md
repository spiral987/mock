# 差分関係の具象化 — 現段階のまとめ

作成日: 2026-08-05
用途: web 試作で試すための設計整理。確定事項・未決事項・反証条件を分けて記述する。

---

## 0. 一行で

レイヤーパネルは、**利用者が手作業で維持している関係**（どのレイヤーがどの状態に属するか）を保持できない。その関係を維持される対象として具象化し、レイヤー構造の上に見えるようにする。

---

## 1. 位置づけの変更点（要確認）

当初の枠組みは「差分管理のためのレイヤーパネルの2次元拡張」だった。実データと文献の検討の結果、次の2点で重心が動いている。**加藤先生に相談すべき事項。**

- **差分（属性軸の並置）から、関係の維持へ。** イテレーションと差分は同じ機構に乗る。両者を分けるのは成果物の性質ではなく利用者にとっての役割であり、役割は時点で変わる（Terry et al. 2004 の指摘）。
- **要求抽出から、相互作用モデルによる位置づけへ。** 設計空間の軸を自分で発明せず、Instrumental Interaction / Substrates の原則表を空間として使う。

差分管理は、この枠組みの主要な適用先として残る（降格ではなく、包含）。

## 3. 理論的枠組み

### 3.1 具象化の2つの側

Instrumental Interaction (Beaudouin-Lafon, CHI 2000) と Interaction Substrates (Mackay & Beaudouin-Lafon, CHI 2025) の原則表。

| 原則 | 命令側（道具になる） | 効果側（基層・制約になる） |
|---|---|---|
| 具象化 | 命令を道具に変える | 命令の効果を基層に変える |
| 多相性 | 命令を複数の型に適用 | 制約を複数の型に適用 |
| 再利用 | 過去の命令を適用 | 過去の効果を適用 |
| 調整 | 発行時に引数を調節（一時的） | 制約をずらす（持続的） |
| 特化 | 引数を固定した専用道具を作る | 対象と制約から雛形を作る |

命令側は簡潔さを、効果側は力を増す。**どちらか一方ではなく対**である点に注意。

核心となる主張: **効果の具象化とは、利用者からシステムへの責任の移譲である。** 利用者は関係を表明し、その維持はシステムが引き受ける。

### 3.2 既存手法の位置

| 手法 | 効果側の具象化 | 問題 |
|---|---|---|
| フォルダ階層＋非表示 | 無し | 関係の維持が全て利用者側 |
| Photoshop レイヤーカンプ | 記録はするが維持しない | レイヤーの識別子を外部に持つため、統合で黙って壊れる。構造が安定した最終段階でしか使えない |
| Figma Variants | 強い | 構造の対応を前提とする。調整の余地がない。「どれも選ばない」を許さない |
| Parallel Paths | 命令側中心 | 効果側が薄い |

**レイヤーカンプの破綻は、本研究の直接の出発点として使える。** 利用者は機能の存在を知った上で使わず、焼き固めを選んでいる（要確認: 元ファイルが CLIP STUDIO なら機能自体が無かった可能性。どちらかで主張の強さが変わる）。

## 4. 設計の中核概念

### 4.1 用語

- **行 (row)** — レイヤー木の節点。既存のレイヤーパネルの1行に対応
- **スロット (slot)** — 行の中に横並びで存在する枠。**中身は部分木**（1枚でも38枚でもよい）。無名・1押しで作成・自由に削除
- **状態 (state)** — 名前を持つ対象。`ver1`, `ver2` に対応
- **所属 (attachment)** — スロットが状態にくっついている関係。**維持される**（スナップショットではない）

### 4.2 規則

1. 横方向はその行のスロットの並びであり、**列ではない**。行ごとに数が違ってよい
2. 状態が持つのは「何列目か」ではなく「**その行のどのスロットか**」。列は揃わなくてよい
3. **スロットが1つしかない行は、全状態で自動的に共有される**。宣言も操作も不要
4. 行は「どのスロットも選ばない」状態を取れる（`かげ` が両方非表示だった事例）
5. どの状態からも参照されないスロットが並んでいてよい（統合の凍結など）
6. 状態を作らずスロットだけ並べれば、それが**局所的な反復**になる。大域と局所は参加行数の違いにすぎず、別機構を要さない
7. 状態を削除すると、付いていたスロットが一斉に外れる
8. 「保存」操作は存在しない。くっつけた時点で参加している

### 4.3 スナップショットとの違い（実装時に最重要）

| | 記録型（レイヤーカンプ / 現状の焼き固め） | 所属型（本設計） |
|---|---|---|
| 差分を足す | 保存し直しが必要 | くっつけた時点で参加 |
| 統合する | 記録の指す先を失う | スロットは残るので無傷 |
| ずれる | 気づけない | 付いていないスロットが見える |
| 状態を消す | 記録が消えるだけ | 付いていたものが一斉に外れる |

**実装上の含意: 状態はレイヤーを指してはならない。行の中のスロットを指すこと。** スロット内部で何枚を1枚に統合しようとスロットは残るため、関係が壊れない。

### 4.4 復元できないもの（意図的な限界）

スロットが保つのは**内容**であり、**見た目ではない**。参加していない行を直せば全状態に反映されるという利点の裏返しで、過去のスロットは周囲の変化を受け続ける。

- スロット**内部**の並べ替え → 影響なし（外から見えない）
- **行そのもの**の並べ替え、親の移動 → 過去の見た目は復元できない

対応方針（案C）: 復元は約束せず、**凍結時のサムネイルだけスロットに添える**。現在の合成と食い違っていることが見えるようにする。Substrates の「調整」と同じ形（制約を外して手動に戻すのではなく、ずれを保持したまま見せる）。midori の「ver1 からずれていた」問題も同じ仕組みで拾える。段階7のサムネイル実装と共用できるため追加費用は小さい。

## 6. web 試作で確かめること（優先順）

理論が答えるのは「何を具象化すべきか」まで。**操作が軽いかどうかには答えない。** 試作はそこを見る。

1. **くっつける動作が1操作で済むか。** 所属を作る／外すのに何手かかるか
2. **スロットが5個並んだときの横幅。** 最初に破綻する箇所
3. **状態切替の予測可能性。** ver2 を押したとき、4行が一斉に変わることが理解できるか。共有されている行が変わらないことが理解できるか
4. **ずれの可視化が読めるか。** 「どの状態にも属していないスロットが選ばれている」が伝わる表示
5. **統合前スロットが所属と同じ機構に乗るか。** 別機構が必要になったら、設計の統一性の主張が崩れる

**結果の読み方の注意:** 触って重かった場合、「具象化すべきでなかった」ではなく「**この見せ方が悪かった**」と読む。理論が出した結論を道具の使い勝手で覆さない。
